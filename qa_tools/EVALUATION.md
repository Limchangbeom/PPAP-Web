# PPAP 서비스 평가 리포트 (8개 기업 기준)

> 테스트 대상: **대기업 3곳** — 삼성전자(GDPR·Controller), 채널톡(GDPR·Processor), 쿠팡(CCPA만) —
> **해외진출 중소/스타트업 3곳** — 캐럿(당근마켓 해외법인, GDPR+CCPA), 스푼라디오(오디오 소셜,
> GDPR+CCPA), 에누마(아동 에듀테크, GDPR+CCPA) — **게임 업종 대·중소 비교쌍 2곳** —
> 크래프톤/PUBG(대기업, GDPR+CCPA), 데브시스터즈(중견/SME, GDPR+CCPA) — 총 8개 기업.
> 대기업 위주 테스트는 사내 법무팀이 이미 인지하고 있을 가능성이 높다는 지적에 따라 SME 3곳을
> 추가했고, 이후 "게임 업종이 PPAP를 가장 필요로 한다"는 리서치 결론(아래 참고)에 따라 같은
> 업종의 대기업/SME 비교쌍을 추가해 검증했다.
> 방법론: `AGENT.md`에 따라 각 기업의 실제 공개 개인정보처리방침/프라이버시 노티스 등을 리서치하여
> `qa_tools/data/*.json`을 구성하고(부족한 부분은 `[가상]` 태그), `qa_tools/run_diagnosis.py`로
> 실제 Flask 앱을 통해 진단 전체 흐름(`/start → /diagnosis → /result`)을 재현했다.
> 전체 리포트: `qa_tools/reports/{samsung,channeltalk,coupang,karrot,spoon,enuma,devsisters,
> krafton-pubg}_report.md`
> 참고: "PPAP이 특히 필요한 업종이 있는가"에 대한 별도 리서치는 `qa_tools/RESEARCH_target_industry.md`
> (결론: 모바일/온라인 게임이 가장 근거가 뚜렷한 우선순위 업종 — 한국의 최대 콘텐츠 수출 업종이면서
> GDPR 위반 1위 유형인 "부적법 동의(광고추적)"의 실제 게임업계 제재 선례가 다수 존재).

## 2. 판정 로직 검증 중 발견한 버그 1건 (수정함)

**증상**: 회사 데이터가 완전한데도 하네스가 1페이지에서 검증 오류로 멈추는 현상 발생 (쿠팡 사례).
**원인**: `diagnosis.html`은 전체 문항을 하나의 `<form>`에 렌더링하고 현재 페이지가 아닌 문항은
CSS로만 숨긴다. 실제 사용자는 "예"를 고르는 즉시 같은 화면 안에서 후속 문항(예: `ccpa_incentive_program`
= "예" → `ccpa_incentive_program_notice` 체크리스트 노출)이 나타나 그 자리에서 답하고 제출하지만,
초기 하네스는 "제출 시점 이전에 서버가 알던 응답" 기준으로만 페이지를 구성해 이 새로 나타난 문항을
누락시켰다.
**조치**: `run_diagnosis.py`를 수정해 회사의 최종 답변 전체로 "고정점(fixed point)" 방식으로
보이는 문항 집합을 먼저 계산한 뒤 페이지를 나누도록 변경. 이후 추가한 3개 기업을 포함해 6개
기업 전부 경고 0건으로 재현 완료.
**참고**: 이 자체는 실서비스 버그는 아니고(실제 브라우저는 JS로 그 자리에서 후속 문항을 보여주므로
정상 동작), 우리 테스트 하네스의 설계 결함이었다. 다만 이 과정에서 "조건부 노출 문항이 매우 많고,
페이지 구분이 사실은 시각적 구분일 뿐 전체가 한 폼"이라는 실제 구조를 명확히 확인했다.

## 2.5 (중요) 사실상 모든 기업이 "위반"으로 찍히는 문항 1건 — GDPR 대상 7/7 기업 전원 재현

**문항**: `gdpr_anonymisation_vs_pseudonymisation` ("8. 익명화와 가명화의 법적 구분 관리") —
"처리 중인 데이터가 완전한 익명화가 이루어져 합리적인 어떤 수단으로도 재식별이 원천적으로
불가능한 상태입니까?" (`diagnostic_content.py`) — `status_map = {"yes": "compliant", "no":
"violation"}`, `visible_if = null`(무조건 노출).

**문제**: 이 문항은 GDPR이 적용되는지 여부를 가르는 **범위(scope) 판단 질문**이다 (완전히
익명화된 데이터는 애초에 GDPR상 "개인정보"가 아니므로 이 진단 자체가 불필요해진다). 그런데
평가 로직은 이를 "위반 여부를 가르는 준수 요건"처럼 취급해 "아니오"(= 우리 데이터는 익명화
되지 않은 식별 가능한 개인정보다, 즉 정상적으로 개인정보를 처리하는 대부분의 실제 서비스의
당연한 답)를 **위반**으로 판정한다. GDPR은 기업에게 "데이터를 완전히 익명화하라"고 요구하지
않는다 — 오히려 개인정보를 적법하게 처리하는 것 자체가 GDPR의 전제이므로, 이 문항은 사실상
**개인정보를 다루는 모든 정상 서비스가 자동으로 위반 1건을 받는 구조**다.

**증거**: GDPR을 포함한 7개 기업(삼성전자, 채널톡, 캐럿, 스푼라디오, 에누마, 데브시스터즈,
크래프톤) **전부**의 리포트에서 이 문항이 동일하게 "위반"으로 나타났다
(`qa_tools/reports/{samsung,channeltalk,karrot,spoon,enuma,devsisters,krafton-pubg}_report.md`의
위반 목록 1번). 서로 다른 리서치 에이전트가 서로 다른 업종·규모의 회사를 독립적으로 조사해
답변을 작성했음에도 **7/7, 100% 재현**되는 것으로 보아, 데이터 문제가 아니라 **문항 설계/
판정 로직 자체의 결함**임이 명확히 확인된다.

**영향**: (1) 모든 기업이 최소 1건의 "위반"을 무조건 갖게 되어 종합 점수가 실제보다 낮게
나오고, (2) "위반" 목록 최상단에 실질적으로 무의미한 항목이 항상 노출되어 진짜 위반 항목의
주목도를 떨어뜨린다.

**개선 제안**: 이 문항을 (a) 완전 익명화 데이터인 경우 이후 GDPR 문항 전체를 스킵하는
**범위 게이트 질문**으로 재설계하거나, (b) 평가축 자체를 삭제하고 순수 정보성 질문으로
전환할 것을 권장한다. 최소한 `"no"`를 `violation`이 아닌 `recommended`/해당없음으로 바꾸는
것만으로도 즉시 개선된다.

## 2.6 (중요) 체크리스트 문항 27개 중 4개는 "전부 미충족"을 정직하게 답할 방법이 없다

**증상 발견 경위**: 데브시스터즈 데이터 작업 중 리서치 에이전트가 "체크리스트 문항에 빈 응답을
주면 페이지 제출이 막힌다"는 현상을 보고했다. 원인을 추적해보니 **테스트 하네스가 아니라 실제
서비스(`app.py`) 자체의 검증 로직 버그**로 확인됐다.

**원인**: `validate_page_questions()`(`app.py:550`)는 `answer_is_present()`가 참이어야 페이지를
통과시키는데, 다중선택(`multi`) 문항에서 체크박스를 0개 선택하면 `answer_is_present([])`가
`False`가 되어 **"응답 안 함"과 동일하게 취급**된다. 즉 "이 체크리스트 항목 중 우리가 충족하는
것은 하나도 없다"(실무적으로 명백한 위반 상태)를 표현할 방법이, 애초에 "해당 없음" 선택지가
없는 문항에는 존재하지 않는다.

**규모**: 전체 45개 다중선택 문항 중 **27개(60%)에 "해당 없음" 류의 선택지가 아예 없다**. 그중
4개는 어떤 응답 경로를 타든 **무조건 노출**되어 모든 사용자가 반드시 마주친다:

- `gdpr_lawful_bases` (2. 귀사에 해당되는 개인정보 처리 근거)
- `gdpr_transfer_notice_requirements` (4-9. 처리방침 또는 수집 고지 포함사항)
- `ccpa_policy_contents` (2-4. 방침 기재사항)
- `ccpa_cookie_controls` (7. 쿠키)

나머지 23개는 `visible_if`로 조건부 노출되지만(예: `gdpr_transfer_bcr_alignment`는 국외이전
메커니즘으로 BCR을 선택해야 나타남), 일단 노출되면 동일한 문제가 재현된다.

**추가 재현**: 이후 진행한 크래프톤(PUBG) 데이터 작업에서도 리서치 에이전트가 독립적으로
동일한 문제를 `ccpa_track_a_policy_lists` 문항에서 맞닥뜨렸다고 보고했다 (해당 없음 선택지가
없어 빈 응답이 미응답으로 처리됨). 서로 다른 에이전트가 서로 다른 문항에서 각자 독립적으로
같은 버그를 발견한 것으로, 재현성이 매우 높은 결함임이 다시 확인된다.

**영향**: 이 4개 문항에서는 "우리 방침에 법정 기재사항이 하나도 없다"거나 "쿠키 관련 요건을
전혀 갖추지 못했다"처럼, **가장 심각한(위반 확정) 상태일수록 오히려 진단을 완료할 수 없고**,
사용자는 진행을 위해 최소 1개는 사실과 다르게 체크할 수밖에 없다. `evaluate_question()`의
checklist 평가 로직 자체는 "선택 0개 → violation"으로 올바르게 설계되어 있으므로(이미 맞는
판정 로직이 있음), 이는 **평가 로직이 아니라 그 앞단의 페이지 검증(`validate_page_questions`)
때문에 막히는 구조적 결함**이다. 2.5의 "무조건 위반"과 정반대 방향(무조건 위반을 등록하지
못하게 막음)이지만 같은 급의 심각도로 판단된다.

**개선 제안**: `validate_page_questions()`에서 `multi` 타입 문항은 "체크박스를 0개 선택하고
제출 버튼을 눌렀다"는 사실 자체를 유효한 응답으로 인정하도록 수정 필요 (예: hidden 필드로
"이 문항을 검토했음" 플래그를 별도로 두거나, 모든 체크리스트 문항에 "해당 사항 없음" 선택지를
표준으로 추가).

## 3. 서비스 자체에 대한 평가

### 3.1 판정 로직의 타당성 — 대체로 양호, 단 스코어링은 거칠다

- 4단계(위반/미흡/충족/권장) 판정과 `single`/`multi_presence`/`checklist` 세 가지 평가 방식은
  합리적으로 설계되어 있고, 각 문항이 실제 GDPR/CCPA 조문 번호를 인용해 근거가 명확하다.
- **개선 필요**: `score_from_items()`가 전체 응답 항목의 상태 점수(위반=0, 미흡=55, 권장=78,
  충족=100)를 **단순 평균**한다 (`app.py:918`). 즉 "쿠키 배너 문구 하나 미흡"과 "민감정보 명시적
  동의 누락(위반)"이 점수에 동일한 가중치로 반영된다. 실무에서는 규제 리스크가 큰 항목(민감정보,
  아동, 국외이전)에 가중치를 더 주는 것이 일반적이며, 현재는 사소한 문항이 많은 규정(GDPR 68문항)이
  구조적으로 점수가 더 후하게 나올 여지가 있다.

### 3.2 문항 커버리지 — 매우 상세하지만 구조적 공백이 있다

109개 문항(GDPR 68 + CCPA 41)은 조문 번호까지 인용할 정도로 깊이가 있고, 국내 GDPR/CCPA
자가진단 도구 중에서는 드물게 상세하다. 다만 코드를 전수 검토한 결과 다음 GDPR 핵심 의무 영역이
**별도 문항으로 존재하지 않는다**:

- **개인정보 침해(유출) 통지** (제33·34조) — 감독기관 72시간 통지, 정보주체 통지 기준이 아예 없음
- **처리활동기록(ROPA)** (제30조) — legal_basis 인용에는 등장하지만 실제 질문 문항은 없음
- **DPO 지정 의무** (제37~39조) — 문항 없음
- **EU 대리인 지정 의무** (제27조, 역외 사업자가 EU에 재화·서비스 제공 시) — 문항 없음
- **정보주체 권리 이행 절차**(열람·정정·삭제·이동권, 제15~20조)를 다루는 독립 섹션 — 국외이전/
  아동/자동화된 결정 섹션에 파편적으로만 등장 (예: `gdpr_third_party_notification`)

이 5가지는 실무 GDPR 감사에서 거의 항상 포함되는 항목이라, 다음 버전에서 "8. 유출 대응",
"9. 거버넌스(ROPA·DPO·EU대리인)" 같은 섹션 추가를 권장한다.

### 3.3 UX/흐름 — 전반적으로 자연스러움, 발견한 이슈 2건

- 진행률 표시, 페이지 검증, 인라인 법령/용어 설명, 응답 간 논리충돌 검사(`find_consistency_issues`)는
  잘 동작한다. 조건부 노출(`visible_if`)도 정확하게 작동함을 6개 기업(대기업 3 + 스타트업 3) 전수
  테스트로 확인했다.
- **이슈 A — 메인 페이지의 "GDPR 역할(Controller/Processor)" 선택이 실질적으로 아무 효과가 없다.**
  `app.py`를 추적한 결과, 이 선택값(`gdpr_role`)은 결과 화면의 표시 라벨에만 쓰이고 어떤 문항의
  `visible_if`에도 참조되지 않는다. 실제 역할 분기는 섹션 3(제3자 제공)의 별도 문항
  `gdpr_third_party_role`(수령자가 지시에 따르는지 여부)에서만 발생하며, 이는 사용자가 처음에
  고른 "우리 회사의 역할"과는 다른, "특정 제3자 제공 건에서 상대방의 역할"을 묻는 별개 개념이다.
  채널톡(Processor로 선정)도 결국 68개 GDPR 문항을 삼성전자와 동일하게 받았고, Processor 특유
  의무(제28조 처리계약 등)는 섹션 3~4에서 사용자가 `gdpr_third_party_role=processor`라고 **직접
  답해야만** 나타난다. 사용자 입장에서는 "처음에 역할을 골랐는데 왜 또 물어보지?"라는 혼란이
  생길 수 있고, 초기 선택이 문항 세트에 반영되지 않는 것은 설계 의도(plan.txt의 "Controller/
  Processor 구분" 요구사항)와 실제 구현 사이의 괴리로 보인다.
- **이슈 B — 결과 화면의 "판정"과 "판단 근거"가 사실상 같은 문장이다.** `evaluate_question()`
  (`app.py:864-872`)에서 `summary`와 `reason` 필드가 모두 `STATUS_SUMMARIES[status]`라는 **문항과
  무관한, 4가지 상태별 고정 문구**를 그대로 담는다. 그런데 `result.html`의 세부 결과 영역에서는
  이를 각각 "판정"과 "판단 근거"라는 **다른 라벨**로 두 번 보여준다(`templates/result.html:144-145`).
  실무자 입장에서는 "이 항목이 왜 미흡으로 판정됐는지"에 대한 문항별 구체적 근거를 기대하게 되는데,
  실제로는 "선택한 응답이 원문 기준상 보완 필요로 해석됩니다" 같은 4종 정형 문구만 두 번 반복해서
  보여주는 셈이다. 반면 "문제가 되는 사항"(`item.issue` = 문항 설명)과 "관련 조문"은 문항별로
  실제 다른 내용이라 유용하다. `reason`/`summary` 중 하나는 제거하거나, 문항별 고유한 "판정 근거"
  텍스트(현재 각 문항 정의에 없음)를 추가하는 것을 권장한다.
- **참고**: "PDF 출력"은 서버가 PDF 파일을 생성하는 것이 아니라 `print_report.html`을 열고
  `window.print()`를 자동 호출하는 방식이다 (브라우저의 인쇄 대화상자를 통해 사용자가 PDF로
  저장). 계획서(`plan.txt`)의 "PDF 리포트 형태로 생성"이라는 표현과는 결이 다를 수 있어, 만약
  서버 사이드에서 파일로 저장·다운로드하는 기능이 필요하다면 별도 구현이 필요하다.

### 3.4 결과 리포트 품질 — 실무 활용 가능한 수준

우선순위(위반→미흡), 문항, 응답 요약, 근거 법령을 함께 보여주는 구조는 실무자가 바로 활용하기
좋다. 규정별 점수와 4단계 카운트를 동시에 보여주는 것도 경영진 보고용으로 적절하다. 3.3의
"판정/판단 근거 중복" 이슈만 개선하면 완성도가 더 높아질 것으로 보인다.

### 3.5 기업 간 비교 — 역할·업종에 따라 판정이 의미 있게 갈렸다

- **채널톡(Processor)**: "자동화된 결정" 섹션에서 위반이 몰렸다 — AI 상담 에이전트(ALF)가 대화의
  최대 80%를 자동 처리한다는 실제 공개 정보를 반영한 결과, 제22조(자동화된 결정) 관련 문항들이
  실제로 유의미하게 작동해 리스크를 짚어냈다. 국외이전 섹션에서도 "한국에 대한 EU 적정성결정은
  있지만 미국 하위처리자로의 재이전 근거는 별도"라는 실제 법적 뉘앙스가 결과에 정확히 반영됐다.
- **쿠팡(CCPA)**: 실제 2026년 한국 개인정보위 제재 사례(쿠팡파트너스의 무단 제3자 방문기록
  수집)를 반영하자 "제3자 제공"과 "수집·이용" 섹션에서 위반이 집중되는, 실제 규제 이슈와 방향이
  일치하는 결과가 나왔다.
- **삼성전자(Controller)**: 대기업다운 성숙한 프로그램(BCR, 쿠키정책, EU DPO)을 반영해 점수가
  가장 높았고, 남은 위반/미흡은 주로 "완전 익명화 여부"나 "미성년자 회원국별 동의연령 확인"처럼
  세부적이고 실무에서도 실제로 자주 놓치는 항목에 몰려, 판정의 결이 현실적이다.

### 3.6 대기업 vs 해외진출 스타트업 — PPAP의 실제 타깃에서 나온 시사점

캐럿·스푼라디오·에누마 3곳은 모두 실제로 "해외 진출은 했지만, 진출국 규모별로 전담 법무/프라이버시
인력을 두기 어려운" 실제 사례였다. 세 곳 모두에서 공통적으로 관찰된 패턴:

- **"국내법 기준 문서 + 해외는 사후 추가"라는 동일한 실패 양상**: 캐럿(미국 CCPA 조항은 상세하나
  GDPR 조항은 전무), 스푼라디오(국문 방침은 한국 개인정보보호법 기준 재이전 근거를 상세히 적어도
  GDPR SCC/적정성결정 개념과는 무관), 에누마(미국 COPPA 중심 방침에 "GDPR"·"CCPA" 단어 자체가
  전혀 등장하지 않음) — 세 회사 모두 **"가장 익숙한 한 개 관할 법제 기준으로 방침을 쓰고, 실제 진출한
  다른 관할 법제는 반영이 누락"**되는 동일한 실패 패턴을 보였다. 이는 PPAP처럼 "여러 관할 법제를 동시에
  대조해주는 자가진단 도구"가 정확히 채워야 할 공백이며, 대기업 3곳(특히 삼성전자)에서는 이런
  관할 법제 간 누락이 상대적으로 적었다.
- **국제이전 근거 미비가 스타트업 3곳 모두에서 반복**: "이전 사실은 밝히지만 SCC/적정성결정 등
  법적 근거는 제시하지 않는다"는 정확히 같은 문제가 캐럿(미 하위처리자)·스푼라디오(Braze 등
  재이전)·에누마("오리건주로 이전될 수 있다"고만 언급)에서 반복됐다. 대기업(삼성전자 BCR, 채널톡
  ISO 인증)과 대비되는 가장 뚜렷한 격차 지점이다.
- **에누마 사례가 보여준 흥미로운 예외**: 에누마는 GDPR/CCPA 특유 조항은 거의 없었지만, 미국
  COPPA(아동 전용 규제)에 특화된 실질적 보호장치(광고 배제, 데이터 미판매, 패런털 게이트)는
  잘 갖춰서, CCPA의 미성년자·판매금지 관련 문항에서는 오히려 대기업 못지않게 "충족" 판정을 받았다.
  즉 스타트업이라고 전 영역이 취약한 게 아니라 **"자신이 이미 대응 중인 인접 규제(COPPA)와 개념이
  겹치는 문항"에서는 스타트업도 충분히 좋은 점수를 받을 수 있음**을 보여준다 — PPAP의 진단이
  실제 준비 수준의 차이를 민감하게 반영한다는 근거이기도 하다.
- **종합 점수가 대기업과 크게 차이 나지 않는 이유**: 위와 같이 스타트업 3곳은 실제로는 관할 법제 간
  공백이 크지만, 2.5의 "만능 위반 문항"과 3.1의 "단순 평균 스코어링"이 위반 항목의 개수 차이를
  점수 차이로 충분히 반영하지 못해(스타트업 3곳 위반 15~16건 vs 삼성전자 2건인데도 점수차는 84 vs 67~68점,
  약 16~17점에 불과) 최종 점수만 보면 실제 격차보다 작아 보인다. **스코어링 가중치 개선(4절
  항목 5)이 특히 중소기업 사용자에게 중요한 이유**이기도 하다 — 지금 구조로는 "우리 점수가
  대기업과 비슷하니 괜찮다"는 잘못된 안도감을 줄 수 있다.

### 3.7 게임 업종 대·중소 비교쌍 — 크래프톤(81점) vs 데브시스터즈(67점)

`RESEARCH_target_industry.md`가 "PPAP이 가장 필요한 업종"으로 지목한 게임 업종에서, 같은
업종의 대기업/SME 비교쌍(크래프톤 vs 데브시스터즈)을 직접 테스트했다. **14점 차이**로, 지금까지
비교한 쌍(삼성전자 84 vs 스타트업 67~68, 약 16~17점 차이) 중에서는 가장 작은 격차이면서도
같은 업종 내 비교라 원인이 뚜렷하게 드러났다:

- **크래프톤**: VeraSafe를 EU/UK GDPR 제27조 대리인으로 공식 지정, SCC 기반 이전, ISO 27001+27701
  동시 인증 — 대기업다운 형식적 거버넌스는 잘 갖춰져 있다. 반면 2022년 안티치트(BattlEye) 자동
  오탐으로 인한 대량 영구밴 사건이 실제로 있었고, 원인 공개나 실질적 인간 재검토 절차가 확인되지
  않아 "자동화된 결정" 섹션에서 위반이 나왔다 — **문서상 거버넌스는 성숙해도 실제 자동화 시스템의
  개별 운영 리스크까지는 못 잡아낸다는 것**을 크래프톤 사례가 보여준다.
- **데브시스터즈**: CCPA 고지가 2021년 이후 갱신되지 않아 CPRA의 '공유(share)' 개념·GPC 대응이
  전무하고, 영문 정책에는 이미 서비스 종료된 광고 SDK(MoPub)가 남아있는 반면 실제로는 다른 SDK
  20여 개가 쓰이는 등 "문서와 실제 운영의 불일치"가 데브시스터즈 쪽에서 더 구체적으로 드러났다.
  구글플레이 데이터 세이프티 라벨은 "수집하는 데이터 없음"이라고 자체 신고했는데, 이는 상세한
  자체 개인정보처리방침과 정면으로 모순된다 — 실무 리소스가 제한된 SME가 여러 창구(방침·앱스토어
  라벨·SDK 실사용) 간 일관성을 유지하기 얼마나 어려운지 보여주는 사례다.
- **시사점**: 같은 업종 내에서도 대기업은 "거버넌스는 있으나 실제 운영 리스크"가, SME는
  "여러 공시 채널 간 불일치"가 주요 감점 사유로 갈렸다 — PPAP의 우선 개선 필요 항목이 규모별로
  실제로 다른 종류의 문제를 짚어낸다는 점에서 진단 로직의 신뢰도를 뒷받침하는 근거다.

## 4. 개선 제안 (우선순위순)

1. **(High) "완전 익명화 여부" 문항의 위반 판정 제거/재설계** (2.5절): GDPR 대상 7/7 기업 전원에서
   재현되는 만능 위반 문항. `"no"` → `violation` 매핑을 제거하거나 범위 게이트 질문으로 전환.
   가장 재현성이 높고 수정 난이도도 낮아 최우선 권장.
2. **(High) 체크리스트 문항의 "전부 미충족" 응답 차단 수정** (2.6절): `validate_page_questions()`가
   다중선택 0개 선택을 "미응답"으로 오인해 페이지 진행을 막는다 (데브시스터즈·크래프톤 작업 중
   서로 다른 문항에서 독립적으로 2차 재현). 최소 4개 문항(`gdpr_lawful_bases`,
   `gdpr_transfer_notice_requirements`, `ccpa_policy_contents`, `ccpa_cookie_controls`)은 모든
   사용자가 무조건 마주치므로, 가장 심각한 위반 상태를 아예 등록할 수 없는 구조적 결함이다.
3. **(Medium) "판정"/"판단 근거" 중복 제거**: `evaluate_question()`에서 문항별 고유 판정 근거를
   추가하거나, UI에서 중복 필드 중 하나를 제거.
4. **(Medium) 초기 GDPR 역할 선택을 문항 세트에 실제로 반영**: 현재는 표시 라벨 용도뿐이므로,
   Controller 전용/Processor 전용 문항(제13·14조 vs 제28조 등)을 초기 선택값으로도 분기하거나,
   혹은 "이 선택은 표시 라벨용이며 실제 역할 판단은 섹션 3에서 진행합니다"라고 안내 문구 추가.
5. **(Medium) 스코어링에 가중치 도입**: 최소한 "민감정보/아동/국외이전" 관련 위반에는 더 큰
   감점을 주는 가중 평균으로 전환 검토. 3.6에서 보듯 현재는 위반 건수가 5배 이상 차이 나도
   (삼성전자 2건 vs 스타트업 15~16건) 종합 점수 차이는 16~17점에 그쳐, 중소기업 사용자에게
   실제보다 안심되는 신호를 줄 수 있다.
6. **(Low~Medium) 커버리지 확장**: 유출통지(제33·34조), ROPA(제30조), DPO 지정(제37~39조),
   EU 대리인(제27조), 정보주체 권리 이행 절차를 별도 섹션으로 추가.
7. **(Low) PDF 산출 방식 명확화**: 현재는 브라우저 인쇄 방식임을 사용자에게 명시하거나, 서버
   사이드 PDF 생성(예: WeasyPrint)으로 전환할지 결정.
